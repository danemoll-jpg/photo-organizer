# CLAUDE.md — Photo Organizer Project

## What this project is
A local tool to organize ~25 years of family photos on a Windows PC. It has multiple phases, each independently useful and independently testable. Build and validate them one at a time, in order — do not jump ahead to Phase 2 or 3 until Phase 1 is working and confirmed by the user.

**Longer-term direction (refinement of the original personal-use framing, not a change of plan): the user is now considering eventually giving this tool to friends/family, or possibly marketing it.** This doesn't change current priorities (the user's own library is still the immediate focus, phases still land one at a time) — it's the user clarifying what they see this becoming as the tool has matured, not a new goal replacing the old one. See the new cross-cutting rule below for the one concrete practice this refinement changes. Don't over-engineer for this now (no packaging/installer/onboarding-wizard work unless explicitly asked), but keep it in mind: code and UI decisions that would embarrass the tool in front of a non-technical friend deserve slightly more care than "good enough for just me."

**Phase 2c design note worth knowing without re-deriving:** the review tool's tag/caption-keyword filters read the live `captions.jsonl` tail (the same in-memory cache Phase 2b already built for showing captions), NOT the DB's `tags`/`photo_tags`/`caption` columns — those columns only reflect whatever `main.py load-captions` last loaded, which lags an in-progress Phase 2 run. This keeps a photo captioned moments ago immediately filterable, consistent with the tool's "always live, no reruns needed" design, but means those two filters can't use a SQL index and fall back to a batched Python scan (see `review_tool.py::_scan_matches`/`_count_matches`/`_all_matching_paths`). GPS/location filtering stays on the cheap indexed/LIKE SQL path instead, since `location_name` is written straight to the DB by `extract-gps`, not staged in a cache. Random-order slideshow navigation (`/api/nav?mode=random`) uses a hand-rolled cycle-walking Feistel-network permutation (`_feistel_permute`) for the common (SQL-only-filtered) case — an O(1)-memory, repeat-free pseudo-random sequence over the filtered set keyed by a client-minted seed, avoiding ever shuffling/storing 100k+ rows server-side — falling back to a small per-seed cached shuffled list only when a tag/caption filter forces a scan anyway.

**One-click restart for `review_tool.py` (follow-up session, builds the tooling rule 11 depends on): `src/port_check.py` gained `kill_pids()`, `wait_for_port_free()`, and `restart_review_tool()`.** One shared mechanism, two front ends, per rule 7: `"Restart Review Tool.bat"` (repo root) shells out to a new `main.py restart-review-tool` CLI command, and the dashboard's Remote Access panel gained a "Force Restart" button next to its existing "Refresh" — both call `restart_review_tool()` directly, no duplicated kill/wait/relaunch logic anywhere else. It finds every process bound to `cfg.review_tool_port` (kills ALL of them, not just one — this project's real incident had four stacked at once), waits for the port to actually free (polls `listening_pids()`, not a fixed sleep), and only then launches a fresh `review_tool.py` with stdout/stderr redirected to `DEVNULL` (so it can't hit the pythonw.exe-None-stdout crash class regardless of which front end — console `python.exe` or console-less `pythonw.exe` — calls it). If the port never actually frees, it deliberately does NOT launch a doomed second instance — it reports failure instead. The dashboard's Force Restart button refreshes the 3-state status indicator immediately after the worker thread reports back, not on the next 5s tick. Tested for real (`tests/test_port_check.py`): real OS processes bound to a real throwaway port, a harmless stand-in script (`tests/_restart_stub_server.py`) standing in for the real Flask app (same "stand-in subprocess" convention as the Phase 2d-follow-up tunnel test), including a real repro of "three simultaneous stale processes on one port" via `SO_REUSEADDR` — the same Windows quirk that let the original four-stale-processes incident happen in the first place.

**Phase 2f: `review_tool.py`'s long-standing structural read-only guarantee now has one deliberate, narrow exception — editable metadata.** Now that Phase 2d's real login exists, any authenticated user can edit a photo/video's caption, tags (full replace), location, and date taken (DB record only — never moves/renames/re-sorts the actual file; the edit form states this explicitly), plus a reversible "Hide from library" flag. This does NOT relax the read-only guarantee for anything else: a brand-new `get_db_write()` connection, used by exactly one route (`POST /api/edit/<file_hash>`), is the only thing in the whole file that ever writes to the DB — every browsing/GET route still exclusively uses the original `get_db()` `mode=ro` connection, unchanged. The write route sits behind the existing auth gate plus its own CSRF check (identical pattern to login/logout — the same `session["_csrf"]` token, reused) and a server-side field-name allow-list (`src/edits.py::EDITABLE_FIELDS`) — never an arbitrary client-supplied column. **The actual protection mechanism is a new append-only `photo_edits` audit table** (file_hash, field_name, old_value, new_value, edited_by, edited_at) — not per-field boolean columns on `photos` — so it doubles as a real audit trail across multiple invited editors. `main.py load-captions` and `src/gps_backfill.py` (both already-shipped, already-tested) were updated to check this table (`src/edits.py::has_manual_edit()`) before applying an automated write to caption/tags/location respectively, skipping (and logging) any field a human has ever touched — permanently, with no expiry or "un-protect" path short of editing it again. Caption and tags are checked **independently** in load-captions (editing one doesn't shield the other); gps_backfill treats gps_lat/gps_lon/location_name as one unit gated by the single "location" edit flag, still marking `gps_checked=1` on a skip so a permanently-protected row isn't rescanned forever. **A real display-layer subtlety, not just a backend one**: caption/tags normally render from the live `captions.jsonl` cache (Phase 2c's design — see below), but Phase 2f's edits land in the DB's `caption`/`tags`/`photo_tags` columns instead — so `_row_to_dict()` now checks `manual_edit_fields()` per row and prefers the DB value the instant either field has been manually edited, otherwise an edit would appear to silently "revert" the next time the (never-edit-aware) cache is read. "Hide from library" adds an `excluded` boolean column to `photos` (default 0) — `_build_filters()`'s new `show_hidden` param is what makes every route (grid/stats/nav/random) exclude it by default and reveal it again on request; Phase 1/1b's rescan-matching logic doesn't reference this column at all, so the hide is safe from ever being silently undone by a future rescan. No dashboard changes — entirely scoped to `review_tool.py`, same precedent as Phase 2c.

**URGENT-fix follow-up session: `review_tool.py` now calls `db.init_db()` at its own startup — it never did before, and that gap is what caused a real total grid outage.** Phase 2f's session added the `excluded` column and `photo_edits` table, but only `main.py`'s commands and `dashboard.py`'s panels ever called `init_db()` (the "safe/idempotent — CREATE TABLE IF NOT EXISTS + any pending migration" call) before touching the DB; `review_tool.py`, being read-only by design, never did, on the reasonable-sounding theory that a read-only tool shouldn't touch schema. Consequence: restarting `review_tool.py` — the exact rule-11 workflow this project uses after any session that touches it — does NOT apply a pending migration. The user's real 167,430-row `data/photo_organizer.db` genuinely still lacked both the `excluded` column and the `photo_edits` table at this session's start (confirmed directly, not assumed), so `_build_filters()`'s new unconditional `excluded = 0` clause and `_row_to_dict()`'s unconditional `manual_edit_fields()` lookup both raised `sqlite3.OperationalError` on every single grid/stats request — a Flask 500 with no useful per-item message, which is exactly what the user saw as "empty grid, no error." **The originally-suspected cause (the migration leaving pre-existing rows `NULL` instead of backfilling to `0`) was checked and is FALSE** — SQLite's `ALTER TABLE ... ADD COLUMN excluded INTEGER NOT NULL DEFAULT 0` (the actual DDL in `src/db.py::_migrate()`) does correctly backfill every existing row to a real `0`, confirmed by reproducing it against a real copy of the production DB, not just a synthetic table. Fixed with two changes: (1) the actual structural fix — `review_tool.py::main()` now calls `init_db(_cfg.db_path_abs, logger=logger)` right after `setup_logging()`, same as every other entry point, so a pending migration is applied on every launch/restart regardless of which entry point a future session happens to touch; (2) `_build_filters()`'s hidden-item clause changed to `(excluded IS NULL OR excluded = 0)` defensively, belt-and-suspenders against a future migration path getting the backfill wrong even though this one doesn't. This is the one place in the file that opens a normal (non-`mode=ro`) connection outside of the Phase 2f edit route — a one-time startup schema check, not a request-handling route, so it doesn't relax the "every GET route is read-only" guarantee described elsewhere in this file. New regression test `tests/test_urgent_empty_grid.py`, built against a hand-written pre-Phase-2f schema (not a fresh schema.sql-created fixture, which would never exercise the actual migration path). **Also worth knowing: this session found no `tests/` file matching the "migration smoke test" this file's Phase 2f entry (below) claims exists** — worth reconciling next time that entry is touched, since a test that actually exercised `review_tool.py`'s own startup path (not just `db.py::init_db()` in isolation) would likely have caught this before it shipped.

**Phase 2g: real video thumbnails in `review_tool.py`'s grid, replacing Phase 2e's generic play-icon placeholder for a processed video.** Two new modules, same shape as GPS extraction's pair: `src/video_thumbnail.py` (the actual decode — `cv2.VideoCapture` first-frame grab, downscale, JPEG-encode) + `src/thumbnail_backfill.py` (the batch loop over video rows, CLI: `main.py extract-thumbnails`, dashboard: a "Phase 2g — Video Thumbnails" panel placed after GPS Extraction, same "own worker thread/progress bar/log tail/logger_name" pattern as every prior batch panel). **New dependency: `opencv-python-headless`** (bundled codec backend, no system ffmpeg install needed — see Environment). **Resumability is deliberately disk-based, not a DB column**: a cache file already at `data/thumbnails/<file_hash>.jpg` means done; a genuinely corrupt/undecodable video gets a sibling `<file_hash>.failed` marker so it isn't retried forever, while a merely-*missing* file at check time gets neither (transient, retried next run) — this is a real, intentional design difference from GPS's `gps_checked` DB column, not an inconsistency; it also means this is the one Phase-2-something batch operation that never writes to the `photos` table at all. `_row_to_dict()` gained a `has_thumbnail` field (video rows only — no extra stat() cost for photos) that `static/review.js`'s grid uses to decide between a real `<img src="/thumbnail/<hash>">` (with a small play-badge overlay so it still reads as a video) and the original placeholder tile — the front end never requests `/thumbnail/<hash>` unless `has_thumbnail` is true, so a broken-image state can't occur by construction. New `/thumbnail/<file_hash>` route added to `review_tool.py`'s auth-gated/401-not-redirect set alongside `/api/*`/`/image/*`/`/video/*`. **A real SQL-precedence bug was caught by this session's own tests, not just inspection**: the video-extensions OR-clause needed explicit parentheses before appending a `--limit`/folder_prefix AND-clause, since SQL's `AND` binds tighter than `OR` — left unparenthesized, the folder restriction silently applied to only the last extension's branch, letting every other extension match regardless of the requested folder. Fixed before this ever reached a real run.

**Follow-up session: fixed real photos displaying upside down/rotated in `review_tool.py`.** Root cause was the classic EXIF-orientation gap — many phones store pixel data in a fixed sensor orientation and record the intended display rotation in the EXIF `Orientation` tag rather than physically rotating pixels; confirmed for real against actual library photos (e.g. `E:\Pics\2015\2015-09\20150914_072059.jpg`, `Orientation=6`), not just a theoretical concern. **Fixed in exactly one place**: `_get_image_bytes()` (the single function both `/image/<hash>` call sites — the grid thumbnail at `?max=400` and the full-size viewer image at `?max=1800`, see `static/review.js` — already shared) now calls `PIL.ImageOps.exif_transpose()` on the decoded image before `.convert("RGB")`/`.thumbnail()`/re-encode. Purely a serving-time transform, confirmed not assumed: the original file's bytes/hash were verified unchanged after being served. **Video thumbnails (Phase 2g) were checked for the analogous container-rotation-matrix issue and found NOT to need a fix** — see Environment's OpenCV note below; `src/video_thumbnail.py` was left untouched. New regression test `tests/test_orientation_fix.py`. `review_tool.py` restarted via `main.py restart-review-tool` at session end, per rule 11.

**Follow-up session: Date Cluster Audit — a new `src/date_audit.py`, detecting and (for two confirmed root causes) fixing batch-date artifacts, triggered by the user finding ~3,273 photos wrongly dated 2023-10-29.** Deliberately scoped to `main.py`/`dashboard.py` only — does not touch `review_tool.py` or the DB schema (reuses Phase 2f's existing `photo_edits` table and `photos.date_taken`/`date_source` columns), so rule 11/12 don't apply here. All CLI + dashboard per rule 10 (`main.py audit-dates {list,inspect,preview-fix,apply-fix,interpolate-preview,interpolate-apply}`; dashboard's new "Date Cluster Audit" panel, collapsed by default, placed after Phase 2g):
- **Detection** (`find_suspicious_clusters()`): day-level (calendar day, not exact timestamp — see the module's own docstring for why exact-timestamp grouping surfaces a different, unrelated old-scanned-photo pattern instead), sorted by count, with a `date_source` breakdown per day. **Real finding, worth knowing without re-deriving**: the fraction of a day's rows resolved via the least-reliable `date_source='filesystem'` fallback turned out to be an unusually strong discriminator on this real library — every huge-count day that's actually a real event (2016-02-18 at 1,909, 2017-04-05 at 1,809, etc.) is 0% filesystem-sourced (real exif/container dates, naturally spread across the day), while the one genuine bug found (2023-10-29) is 100% filesystem-sourced.   - **Real bug hit and fixed:** linking the raw `photos` table showed every row as `#Deleted` in Access.   - **Treat the Access link as read-only browsing.** `photo_organizer.db` gets written to by every Phase 1/1b/2 run; editing a row in Access while a real run is active risks a write conflict. Not enforced in code (Access can technically write through an updatable view/table) — just a documented usage convention.
  - If a future schema change adds another REAL/float column, expect the same `#Deleted` issue on it via Access unless it's also cast to TEXT in `photos_access` (or a future replacement view). Known instance already sitting in the schema: `photo_tags.confidence` — expect `#Deleted` there too if the user ever links `photo_tags` directly; no fix view built for it yet since not requested.
  - **DSN persistence bug hit and worked around:** the SQLite3 ODBC Driver's own config GUI (`ODBC Data Sources (64-bit)` → System DSN → Configure) silently failed to save the `Database` path — it kept showing blank on reopen even after going through the dialog (twice, once after explicitly re-running it elevated). Worked around by writing the registry value directly: `HKLM:\SOFTWARE\ODBC\ODBC.INI\SQLite3 Datasource\Database` via `New-ItemProperty ... -Force` (user ran this themselves, a system-setting change). Also hit and ruled out along the way: an `IM006`/`SQLSetConnectAttr failed`/"out of memory" error, which generically indicates the ODBC Driver Manager failing to set a connection attribute after connecting (commonly connection-pooling-related) — pooling was already disabled for this driver on this machine, so that wasn't the actual cause here; the real fix was just getting the Database path to actually persist. Worth knowing if ODBC linking ever needs to be redone or done on another machine: **don't trust the driver's own config dialog to have saved anything — verify the registry value directly afterward** (`Get-ItemProperty "HKLM:\SOFTWARE\ODBC\ODBC.INI\SQLite3 Datasource"`).
  - **There are three similarly-named SQLite ODBC DSNs pre-installed by the driver package**, easy to confuse: `SQLite3 Datasource` (`sqlite3odbc.dll` — correct, SQLite3-compatible, this is the one to use), `SQLite Datasource` and `SQLite UTF-8 Datasource` (`sqliteodbc.dll`/`sqliteodbcu.dll` — legacy SQLite **2** drivers, incompatible with this project's SQLite3 database file). Always use `SQLite3 Datasource`.

## Non-negotiable cross-cutting rules
1. **Resumability everywhere.** Every phase must be safely re-runnable without redoing work already done. Track processed files by content hash, not filename or path. (See the destination-rescan performance issue above — resumability shouldn't mean "safe but needlessly slow"; cheap pre-checks before a full hash are in scope for satisfying this rule well, not just technically.)
2. **Never silently overwrite or destroy original photos.** Phase 1 uses copy-verify-delete: copy to destination, verify via hash comparison, only then delete the source. A failed verification must leave the source in place and get logged — never delete on an unverified copy. Collision handling must never overwrite an existing file.
3. **Log everything.** Every phase needs a log the user can read after the fact to answer "what happened to file X and why." The dashboard's log viewer reads these same log files — don't create a second, separate logging path for the GUI.
4. **Config, not hardcoding.** Source/dest paths, backend choice (local model vs Claude API for captioning), batch sizes, and GPU on/off should live in a config file.
5. **JSONL for intermediate outputs** (Phase 2 captions, Phase 3 face embeddings) — appendable, resumable. SQLite is the final data layer, loaded from JSONL.
6. **Primary key = file content hash** across all DB tables, since paths will move during Phase 1 and duplicates/re-exports are likely across 25 years of photos.
7. **The GUI is a wrapper, not a parallel implementation.** The dashboard should call the same underlying functions/modules the CLI uses, not duplicate logic. `main.py`'s commands must keep working directly.
8. **At 100k+ files, favor batched/incremental real runs over one giant pass**, and favor cheap pre-checks (path/size/mtime) over full re-hashing wherever a file is very likely unchanged. Both the CLI and dashboard already support scanning a subset of `source_folders`, so folder-by-folder real runs are achievable without new code.
9. **Video (Phase 1b) reuses Phase 1's copy-verify-delete/hashing/collision/logging logic as-is — do not reimplement any of it for video.** Only the date-resolution first step (container metadata vs. EXIF) and the destination subfolder routing are actually different.
10. **Every user-facing capability must be exposed in the dashboard — not left CLI-only.** This was violated once already (GPS extraction shipped as `main.py extract-gps` with no dashboard button, and the user only discovered this after being confused why location data wasn't showing up) and the user explicitly corrected it going forward: from now on, when a session adds a new capability the user would actually want to run themselves (not an internal/dev-only script), it needs a dashboard panel or button in the SAME session that builds it — not deferred to "add a GUI for it later." CLI commands can still exist alongside (main.py stays fully usable per rule 7), but the dashboard must never be missing something the CLI can do that an end user would want.
11. **When a session modifies `review_tool.py` (or its templates/static/supporting modules), it must restart it itself before ending the session — not leave that for the user to do manually.** This is an explicit reversal of the earlier "don't kill a process you didn't start unprompted" convention, scoped specifically to `review_tool.py`: the user has explicitly requested this automation given how often stale processes serving pre-change code have caused confusion in this project. Use the restart tooling being built for this purpose (see TODO.md's "One-click restart" item) — detect any process bound to the configured `review_tool_port`, kill it/them, wait for the port to actually free, then relaunch fresh — so the session's own changes are immediately live and testable without any manual step. This does NOT extend to `dashboard.py` or any other process — the reversal is scoped to `review_tool.py` only, since it's stateless/read-only and safe to restart unprompted; other processes still follow the original "don't touch what you didn't start" convention.
12. **Every entry point that opens the DB must call `db.init_db()` first, no exceptions — including read-only ones.** Added after a real total outage: `review_tool.py` was the one entry point that never called it (reasonable-sounding theory: "a read-only tool shouldn't touch schema"), so a schema-adding session (Phase 2f's `excluded` column + `photo_edits` table) left the real production DB permanently unmigrated across a `review_tool.py`-only restart — rule 11's own restart workflow doesn't imply a migration happened. `init_db()`/`_migrate()` are safe/idempotent (`CREATE TABLE IF NOT EXISTS` + additive `ALTER TABLE`, never destructive) precisely so that every caller, read-only or not, can call it unconditionally at startup with no downside. If a future entry point is added (another script, another tool), it calls `init_db()` before its first query — full stop, don't reason your way into an exception the way this one did.
