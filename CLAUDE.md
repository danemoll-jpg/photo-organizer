# CLAUDE.md — Photo Organizer Project

## What this project is
A local tool to organize ~25 years of family photos on a Windows PC. It has multiple phases, each independently useful and independently testable. Build and validate them one at a time, in order — do not jump ahead to Phase 2 or 3 until Phase 1 is working and confirmed by the user.

**Structural note:** Phase 1 originally shipped as a CLI (`main.py` with subcommands). It now also has a desktop dashboard (`dashboard.py`, Tkinter) that wraps the same underlying code (`src/organize.py`, `src/pick_sources.py`, `src/config.py`, `src/db.py`, `src/logging_setup.py`, and — as of Phase 2 — `src/caption.py`) — the CLI was not replaced or removed, both remain fully usable. Launch via `Launch Dashboard.bat` (repo root) or the "Photo Organizer" Desktop shortcut — both run `dashboard.py` through `pythonw.exe` (no console window). **The dashboard now has a Phase 2 (captioning) panel too** — don't assume Phase 2 is CLI-only; it was CLI-only for part of this session until the user hit real confusion using the dashboard's Phase 1 "Run" button expecting it to caption, so a proper panel was added (see TODO.md). See TODO.md for current scope and README.md for panel-by-panel usage.

Driver-level check confirmed working (`nvidia-smi` shows the GTX 1660 Ti, WDDM driver, CUDA 13.3 runtime supported). Framework-level check (e.g. `torch.cuda.is_available()` or onnxruntime-gpu's equivalent) is still needed once Phase 3 picks a library — don't assume driver-level success means the framework will see the GPU too.
- `pywin32`'s shell wrapper does NOT expose `IFileDialog`/`IFileOpenDialog` for Python 3.14 — only the lower-level `IShellItem`/`IShellItemArray`. The native multi-select folder picker hand-declares the COM vtable interfaces via `comtypes` instead (see `src/folder_picker.py` docstring). Worth remembering if any future COM/shell work comes up.
- `hachoir>=3.3` (Phase 1b's video container-metadata reader) installs cleanly as a pure-Python wheel on this machine's Python 3.14 venv — no compat issues, unlike the GPU-framework caveat above.
- **Ollama (Phase 2 backend) is now installed** — wasn't on this machine before Phase 2's session. Installed via `winget install Ollama.Ollama` (v0.33.3), which auto-starts it as a background service (reachable at `http://localhost:11434` with no manual `ollama serve` needed). The `ollama` pip package (v0.6.2, pure-Python wheel, pulls in `httpx`+`pydantic`) installs cleanly on this machine's Python 3.14 venv too — same "verify wheel availability" caution as the GPU-framework note above, confirmed fine here.
- **Models pulled and confirmed working on the GTX 1660 Ti:** `qwen3-vl:2b` (1.9GB, configured default) and `minicpm-v4.6` (its `:1b` tag, 1.6GB, fallback). Both fully GPU-resident (`ollama ps` shows 100% GPU). **Correction to an earlier session's note:** the fallback's correct pull name is `minicpm-v4.6`, not `minicpm-v:4.6` — `minicpm-v`'s own tag list tops out at 8B/5.5GB+ with no 4.6 variant; `minicpm-v4.6` is its own separate model name in Ollama's library.
- **Real Phase 2 throughput on this hardware: ~7-9s/image steady-state** (qwen3-vl:2b, `think=False`, 1024px-downscaled images) — at 100k+ files that's roughly 8-9 days of continuous run time. Budget for a multi-day/multi-week background job, not an overnight pass.
- **qwen3-vl is a "thinking" model by default — leave it OFF for captioning.** With thinking enabled, per-image latency was ~3x worse (~17-22s vs ~7-9s) because the model spends most of its time on hidden chain-of-thought before ever emitting the actual answer. `src/caption.py` always passes `think=False` to every model (confirmed harmless/ignored on `minicpm-v4.6`, which has no thinking mode).
- **Real Ollama quirk hit and worked around:** with `think=False` AND a JSON-schema `format` together, `qwen3-vl:2b` sometimes puts its answer in `message.thinking` instead of `message.content` (confirmed against Ollama 0.33.3) — an apparent interaction bug between those two options for this model. `src/caption.py::_caption_one()` reads `content` first, falls back to `thinking`. `minicpm-v4.6` doesn't have this quirk. Worth re-checking if a future Ollama/model update might have fixed it (the fallback logic is harmless either way, so no urgency to remove it).
- **Real small-model limitation observed, not just theoretical:** on a low-detail synthetic test image (solid black square), `qwen3-vl:2b` confidently hallucinated an entirely wrong, detailed scene rather than describing the actual flat color. Expected to matter less on real photos (which have actual content to work from), but worth watching for during the real-sample quality review, not just the already-expected "simple tags, not vivid captions" tradeoff.
- **`qwen3-vl:2b` vs `minicpm-v4.6` head-to-head on the same 6 real sample photos — qwen3-vl:2b wins, keep it as the default.** Speed was a wash (6.5s vs 6.7s/image, within noise). Quality was not: `minicpm-v4.6` twice returned tags that were literally the prompt's own category placeholder words ("season", "objects", "subjects", "place", "activity") instead of real content-derived tags, and once produced a garbled non-word tag ("ridgelike") — a similar failure mode to the schema-echoing bug seen earlier with `qwen3-vl:2b` on a degenerate synthetic image, but happening here on ordinary real photos. `qwen3-vl:2b`'s captions/tags were consistently more specific and reliable across all 6. No reason to switch found.
- **Real bug found and fixed via this comparison:** `_preflight_check()` in `src/caption.py` did an exact string match against `ollama list`'s model names, but Ollama always reports a tag (an untagged pull like `minicpm-v4.6` shows up as `minicpm-v4.6:latest`) — so any config value without an explicit `:tag` failed preflight even though the actual `chat()` call would have worked fine. Fixed by comparing with `:latest` implied on whichever side lacks a tag. Worth remembering if a future model gets added to config without a tag suffix.
- **SQLite ODBC Driver (64-bit) installed** — `sqliteodbc_w64.exe` from ch-werner.de, for the user's MS Access linked-table setup (see Data access notes below). A user-side tool, not a project dependency — nothing in `src/` or `requirements.txt` depends on it.
- **Recurring bug pattern, now hit twice: a third-party library doing its own console output crashes under `pythonw.exe`.** The dashboard launches via `pythonw.exe` (no console — see `Launch Dashboard.bat`), so `sys.stdout`/`sys.stderr` are `None` there. First hit: `tqdm` (fixed by moving progress reporting to a `progress_cb` callback instead). Second hit: `hachoir`'s own internal warning/error logging writes straight to `sys.stdout`/`sys.stderr` unconditionally, crashing on ANY hachoir warning (routine — e.g. an unusual/corrupt video container, expected at this library's scale). Fixed in `src/video_date_resolver.py` by disabling hachoir's print path at import time (`hachoir.core.config.quiet = True` plus `hachoir.core.log.log.use_print = False` — quiet alone doesn't cover LOG_ERROR). **Check for this pattern with any future third-party library** brought in for a phase that might run under the dashboard: does it print/log to stdout/stderr on its own, and if so, does it guard against those being `None`?

- **MS Access ODBC link is now set up and working (done ad hoc mid-Phase-2-session, at the user's request — not itself a phase deliverable).** See README.md's "Viewing the database" section for full setup steps. Key facts to know without re-deriving:
  - Driver: the SQLite ODBC Driver from ch-werner.de (`sqliteodbc_w64.exe`, 64-bit to match this machine's 64-bit Office/Access) — installed via its own installer (needs admin/UAC, not winget-packaged). Not a project dependency, purely a user-side tool.
  - **Real bug hit and fixed:** linking the raw `photos` table showed every row as `#Deleted` in Access. Cause: the SQLite ODBC driver doesn't reliably expose `file_hash`'s PRIMARY KEY to Access as a usable unique row identifier, so Access falls back to matching a row by comparing every column's value — and `file_mtime` (REAL/float) doesn't round-trip byte-for-byte through ODBC, so that match silently fails on every row. **Fix: added a `photos_access` view to `schema.sql`** (`CAST(file_mtime AS TEXT)`, everything else passed through) — link that instead of `photos`. Confirmed fixed by the user. Purely additive (a view, always reflects live data, not a copy/snapshot) and read-only in Access (which is fine/intended — see next point).
  - **Treat the Access link as read-only browsing.** `photo_organizer.db` gets written to by every Phase 1/1b/2 run; editing a row in Access while a real run is active risks a write conflict. Not enforced in code (Access can technically write through an updatable view/table) — just a documented usage convention.
  - If a future schema change adds another REAL/float column, expect the same `#Deleted` issue on it via Access unless it's also cast to TEXT in `photos_access` (or a future replacement view).

## Non-negotiable cross-cutting rules
1. **Resumability everywhere.** Every phase must be safely re-runnable without redoing work already done. Track processed files by content hash, not filename or path. (See the destination-rescan performance issue above — resumability shouldn't mean "safe but needlessly slow"; cheap pre-checks before a full hash are in scope for satisfying this rule well, not just technically.)
2. **Never silently overwrite or destroy original photos.** Phase 1 uses copy-verify-delete: copy to destination, verify via hash comparison, only then delete the source. A failed verification must leave the source in place and get logged — never delete on an unverified copy. Collision handling must never overwrite an existing file.
3. **Log everything.** Every phase needs a log the user can read after the fact to answer "what happened to file X and why." The dashboard's log viewer reads these same log files — don't create a second, separate logging path for the GUI.
4. **Config, not hardcoding.** Source/dest paths, backend choice (local model vs Claude API for captioning), batch sizes, and GPU on/off should live in a config file.
5. **JSONL for intermediate outputs** (Phase 2 captions, Phase 3 face embeddings) — appendable, resumable. SQLite is the final data layer, loaded from JSONL.
6. **Primary key = file content hash** across all DB tables, since paths will move during Phase 1 and duplicates/re-exports are likely across 25 years of photos.
7. **The GUI is a wrapper, not a parallel implementation.** The dashboard should call the same underlying functions/modules the CLI uses, not duplicate logic. `main.py`'s commands must keep working directly.
8. **At 100k+ files, favor batched/incremental real runs over one giant pass**, and favor cheap pre-checks (path/size/mtime) over full re-hashing wherever a file is very likely unchanged. Both the CLI and dashboard already support scanning a subset of `source_folders`, so folder-by-folder real runs are achievable without new code.
9. **Video (Phase 1b) reuses Phase 1's copy-verify-delete/hashing/collision/logging logic as-is — do not reimplement any of it for video.** Only the date-resolution first step (container metadata vs. EXIF) and the destination subfolder routing are actually different.

## Session model
- The user runs a **fresh Code session for each phase** (to keep individual sessions from ballooning). This means CLAUDE.md must always contain full standing context — don't assume memory of prior sessions.
- TODO.md is scoped to the current active phase only. Work only within that phase. Do not start, scaffold, or "get ahead" on later phases even if it seems efficient — the user and Claude (chat) review and re-scope TODO.md between sessions before the next phase begins.
- If something in a later phase is blocked or ambiguous because of a decision only that phase would resolve, flag it in your summary at the end of the session rather than jumping ahead to resolve it.
- **Always keep TODO.md current as work happens** — check items off as they're completed, add new sub-tasks if scope details get decided mid-session, and note any judgment calls made along the way so they're visible rather than buried in code.
- **Update CLAUDE.md too when something durable changes** — a structural decision, a new confirmed environment fact, or a new cross-cutting rule belongs here, not just in TODO.md. TODO.md is for task status; CLAUDE.md is for standing context that the next fresh session needs to know without being told again.
- End every session with a written summary: what was built/changed, what was tested and how, and anything the user or the next session should know. This is in addition to updating the files themselves, not instead of it.
