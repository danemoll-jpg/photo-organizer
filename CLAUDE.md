# CLAUDE.md — Photo Organizer Project

## What this project is
A local tool to organize ~25 years of family photos on a Windows PC. It has multiple phases, each independently useful and independently testable. Build and validate them one at a time, in order — do not jump ahead to Phase 2 or 3 until Phase 1 is working and confirmed by the user.

**Longer-term direction (refinement of the original personal-use framing, not a change of plan): the user is now considering eventually giving this tool to friends/family, or possibly marketing it.** This doesn't change current priorities (the user's own library is still the immediate focus, phases still land one at a time) — it's the user clarifying what they see this becoming as the tool has matured, not a new goal replacing the old one. See the new cross-cutting rule below for the one concrete practice this refinement changes. Don't over-engineer for this now (no packaging/installer/onboarding-wizard work unless explicitly asked), but keep it in mind: code and UI decisions that would embarrass the tool in front of a non-technical friend deserve slightly more care than "good enough for just me."

**Structural note:** Phase 1 originally shipped as a CLI (`main.py` with subcommands). It now also has a desktop dashboard (`dashboard.py`, Tkinter) that wraps the same underlying code (`src/organize.py`, `src/pick_sources.py`, `src/config.py`, `src/db.py`, `src/logging_setup.py`, and — as of Phase 2 — `src/caption.py`) — the CLI was not replaced or removed, both remain fully usable. Launch via `Launch Dashboard.bat` (repo root) or the "Photo Organizer" Desktop shortcut — both run `dashboard.py` through `pythonw.exe` (no console window). **The dashboard now has a Phase 2 (captioning) panel too** — don't assume Phase 2 is CLI-only; it was CLI-only for part of this session until the user hit real confusion using the dashboard's Phase 1 "Run" button expecting it to caption, so a proper panel was added (see TODO.md). See TODO.md for current scope and README.md for panel-by-panel usage.

**A third front end now exists, deliberately separate from both of the above: `review_tool.py` (Phase 2b, extended by Phase 2c).** It's a standalone local Flask web app (`venv\Scripts\python review_tool.py`, opens `http://127.0.0.1:5151` in a browser), not a dashboard panel and not a CLI subcommand — the user explicitly wanted it separate, and per the dashboard rule below, Phase 2c's additions stayed scoped to this tool too (not something an end user would run any other way). It's read-only (SQLite opened via `mode=ro`; `captions.jsonl` only ever tailed for reading) and lets the user browse/paginate/filter the library and spot-check Phase 2's in-progress captioning live, plus a photo viewer/slideshow mode with random navigation and rich filtering (Phase 2c: tag, caption keyword, GPS/location, plus a visible-but-inert people/faces placeholder — see TODO.md's Phase 2c section). See TODO.md's Phase 2b/2c sections and README.md for full detail. A second, independent piece of Phase 2b — `main.py extract-gps` — writes GPS/location data into the DB (the review tool only displays it); that command is separate from `review_tool.py` on purpose, since the review tool itself must stay read-only.

**Phase 2d (remote/shared access) added three things to `review_tool.py`, all scoped to it alone — not the dashboard, not Phase 1/1b/2:** (1) real session-based login (`src/auth.py`) gating every route except `/login`/`/logout`/`/static/*`, backed by `config.yaml`'s `review_users` (username + hashed password, managed via `main.py review-user add/list/remove`, never hand-edited); (2) a `PhotoStorage` abstraction (`src/storage.py`, local-disk-only today) between `review_tool.py` and the filesystem, groundwork for a possible future cloud-storage backend; (3) a Cloudflare Tunnel for HTTPS remote access, independent of Plex's own remote-access setup. See TODO.md's Phase 2d section for the full design reasoning (rate limiting, CSRF, open-redirect guard, timing-safe unknown-username handling) and exactly what is/isn't done yet (no `review_users` entry added, tunnel not yet connected to the user's Cloudflare account).

**Phase 2c design note worth knowing without re-deriving:** the review tool's tag/caption-keyword filters read the live `captions.jsonl` tail (the same in-memory cache Phase 2b already built for showing captions), NOT the DB's `tags`/`photo_tags`/`caption` columns — those columns only reflect whatever `main.py load-captions` last loaded, which lags an in-progress Phase 2 run. This keeps a photo captioned moments ago immediately filterable, consistent with the tool's "always live, no reruns needed" design, but means those two filters can't use a SQL index and fall back to a batched Python scan (see `review_tool.py::_scan_matches`/`_count_matches`/`_all_matching_paths`). GPS/location filtering stays on the cheap indexed/LIKE SQL path instead, since `location_name` is written straight to the DB by `extract-gps`, not staged in a cache. Random-order slideshow navigation (`/api/nav?mode=random`) uses a hand-rolled cycle-walking Feistel-network permutation (`_feistel_permute`) for the common (SQL-only-filtered) case — an O(1)-memory, repeat-free pseudo-random sequence over the filtered set keyed by a client-minted seed, avoiding ever shuffling/storing 100k+ rows server-side — falling back to a small per-seed cached shuffled list only when a tag/caption filter forces a scan anyway.

**One-click restart for `review_tool.py` (follow-up session, builds the tooling rule 11 depends on): `src/port_check.py` gained `kill_pids()`, `wait_for_port_free()`, and `restart_review_tool()`.** One shared mechanism, two front ends, per rule 7: `"Restart Review Tool.bat"` (repo root) shells out to a new `main.py restart-review-tool` CLI command, and the dashboard's Remote Access panel gained a "Force Restart" button next to its existing "Refresh" — both call `restart_review_tool()` directly, no duplicated kill/wait/relaunch logic anywhere else. It finds every process bound to `cfg.review_tool_port` (kills ALL of them, not just one — this project's real incident had four stacked at once), waits for the port to actually free (polls `listening_pids()`, not a fixed sleep), and only then launches a fresh `review_tool.py` with stdout/stderr redirected to `DEVNULL` (so it can't hit the pythonw.exe-None-stdout crash class regardless of which front end — console `python.exe` or console-less `pythonw.exe` — calls it). If the port never actually frees, it deliberately does NOT launch a doomed second instance — it reports failure instead. The dashboard's Force Restart button refreshes the 3-state status indicator immediately after the worker thread reports back, not on the next 5s tick. Tested for real (`tests/test_port_check.py`): real OS processes bound to a real throwaway port, a harmless stand-in script (`tests/_restart_stub_server.py`) standing in for the real Flask app (same "stand-in subprocess" convention as the Phase 2d-follow-up tunnel test), including a real repro of "three simultaneous stale processes on one port" via `SO_REUSEADDR` — the same Windows quirk that let the original four-stale-processes incident happen in the first place.

**Phase 2e: video rows are now included in `review_tool.py` (grid/viewer/stats), reversing Phase 2b's original exclusion.** The exclusion had been a single bolted-on `AND` clause (`_video_exclusion_sql()`/`_video_exclusion_params()`, now removed) in `_build_filters()` — every other query helper (`_fetch_page`, `_count_matches`, `_pick_random_row`, `_feistel_permute`, `_random_order_for`) was never video-aware to begin with, so removing that one clause was sufficient; no other backend changes were needed for filters/nav/random/slideshow to work uniformly across photos and video. Front-end-only changes handle display: `static/review.js` shows "No caption" (not "Not yet captioned") for an uncaptioned video, a play-icon placeholder in the grid instead of a thumbnail, and swaps in a real `<video>` element in the viewer (via a new `/video/<file_hash>` route in `review_tool.py`, alongside the existing `/image/<file_hash>` for photos). The new route needed one small addition to `src/storage.py::PhotoStorage`: a `local_path()` method (default `None`, overridden by `LocalDiskStorage` to return the real path) so `send_file(..., conditional=True)` can serve HTTP Range requests for scrubbing — `/image/<hash>` never needed this since it already fully decodes into memory via PIL regardless. `src/auth.py`'s before_request 401-not-redirect handling (previously `/api/*`/`/image/*`) now also covers `/video/*`, same reasoning. Location for video needed no code change at all — `gps_backfill.py` already processes video rows like any other file and always finds nothing, so a checked video row already fell into the existing "No location available" text, not a new case.

- **qwen3-vl is a "thinking" model by default — leave it OFF for captioning.** With thinking enabled, per-image latency was ~3x worse (~17-22s vs ~7-9s) because the model spends most of its time on hidden chain-of-thought before ever emitting the actual answer. `src/caption.py` always passes `think=False` to every model (confirmed harmless/ignored on `minicpm-v4.6`, which has no thinking mode).
- **Real Ollama quirk hit and worked around:** with `think=False` AND a JSON-schema `format` together, `qwen3-vl:2b` sometimes puts its answer in `message.thinking` instead of `message.content` (confirmed against Ollama 0.33.3) — an apparent interaction bug between those two options for this model. `src/caption.py::_caption_one()` reads `content` first, falls back to `thinking`. `minicpm-v4.6` doesn't have this quirk. Worth re-checking if a future Ollama/model update might have fixed it (the fallback logic is harmless either way, so no urgency to remove it).
- **Real small-model limitation observed, not just theoretical:** on a low-detail synthetic test image (solid black square), `qwen3-vl:2b` confidently hallucinated an entirely wrong, detailed scene rather than describing the actual flat color. Expected to matter less on real photos (which have actual content to work from), but worth watching for during the real-sample quality review, not just the already-expected "simple tags, not vivid captions" tradeoff.
- **`qwen3-vl:2b` vs `minicpm-v4.6` head-to-head on the same 6 real sample photos — qwen3-vl:2b wins, keep it as the default.** Speed was a wash (6.5s vs 6.7s/image, within noise). Quality was not: `minicpm-v4.6` twice returned tags that were literally the prompt's own category placeholder words ("season", "objects", "subjects", "place", "activity") instead of real content-derived tags, and once produced a garbled non-word tag ("ridgelike") — a similar failure mode to the schema-echoing bug seen earlier with `qwen3-vl:2b` on a degenerate synthetic image, but happening here on ordinary real photos. `qwen3-vl:2b`'s captions/tags were consistently more specific and reliable across all 6. No reason to switch found.

- **Recurring bug pattern, now hit three times: something doing its own console I/O misbehaves under `pythonw.exe`.** The dashboard launches via `pythonw.exe` (no console — see `Launch Dashboard.bat`), so `sys.stdout`/`sys.stderr` are `None` there. First hit: `tqdm` (fixed by moving progress reporting to a `progress_cb` callback instead). Second hit: `hachoir`'s own internal warning/error logging writes straight to `sys.stdout`/`sys.stderr` unconditionally, crashing on ANY hachoir warning (routine — e.g. an unusual/corrupt video container, expected at this library's scale). Fixed in `src/video_date_resolver.py` by disabling hachoir's print path at import time (`hachoir.core.config.quiet = True` plus `hachoir.core.log.log.use_print = False` — quiet alone doesn't cover LOG_ERROR). **Third hit, a different flavor of the same class — a real bug found and fixed this follow-up session:** `src/port_check.py::listening_pids()` calls `subprocess.run(["netstat", ...])` with no `creationflags`. Spawning a console app (`netstat.exe`) from a process with no console of its own (pythonw.exe) makes Windows create a brand-new console window for the child — and the Remote Access panel's status check calls this every 5 seconds for as long as the dashboard is open (`self._port_status_tick`, scheduled unconditionally in `__init__`, independent of whether that panel is even expanded or what else is running), so this was a console window flashing open/closed every 5 seconds and stealing focus for the dashboard's entire lifetime. Confirmed via a repro harness (pythonw.exe + a tight polling loop counting `conhost.exe`/`netstat.exe` process instances) that this really does spawn a transient console, and that adding `creationflags=getattr(subprocess, "CREATE_NO_WINDOW", 0)` — the exact flag `dashboard.py`'s own `cloudflared` `Popen` call already used for this same reason — eliminates it. **This one was initially misdiagnosed as GPS-extraction-specific** (see TODO.md's "PRIORITY BUG #1") purely because the Remote Access panel and the GPS panel were both introduced in nearby follow-up sessions and the user started exercising both around the same time — the actual timer runs regardless of GPS. **Check for this pattern with any future third-party library or subprocess call** brought in for a phase that might run under the dashboard: does it print/log to stdout/stderr on its own (guard against `None`), or spawn a child console process (needs `CREATE_NO_WINDOW`)?
- **A second, unrelated real bug in the same follow-up session's "GPS logging in the wrong panel" report: `src/logging_setup.py::setup_logging()` used a single shared, hardcoded `logging.getLogger("photo_organizer")` singleton.** The dashboard's Phase 1/Captioning/GPS-extraction worker threads can genuinely run concurrently (an explicitly supported combination — see the GPS Extraction panel note above), but every `setup_logging()` call cleared and repointed that ONE shared logger's handler at its own new log file — so whichever worker called it most recently silently redirected every OTHER already-running worker's subsequent log lines into that file too. In the user's real hit, GPS extraction had been running for a while when Captioning was started, which "stole" the shared logger — so GPS's own ongoing log lines started landing in the Captioning panel's log box/file instead of GPS's own, even though the panels' queue-dispatch/tail-widget routing (which panel's Text widget shows which file) was actually correct all along; the TODO.md item's original "copy-paste in the dispatch logic" theory was wrong. **Fixed via a `logger_name` parameter on `setup_logging()`** (`logger.propagate = False` too, so a child logger's messages can't leak up into a same-named ancestor another worker might be using) — `dashboard.py`'s three worker threads now each pass a distinct name (`photo_organizer.organize`/`.caption`/`.gps`), giving each its own independent `Logger` object immune to a sibling worker calling `setup_logging()` later. `main.py`/`review_tool.py` keep calling it with the default name unchanged (each runs one thing at a time in its own process, so there's no shared-object risk there). **A second contributing bug found while testing fix #1 and fixed alongside it:** `new_log_path()`'s timestamp was second-resolution only (`%Y%m%d_%H%M%S`) — two `setup_logging()` calls within the same wall-clock second (e.g. clicking Start on two panels in quick succession) produced an IDENTICAL filename, so even with two independent `Logger` objects, their two `FileHandler`s would silently both append to the one physical file, undoing fix #1's isolation. Now microsecond-resolution (`%Y%m%d_%H%M%S_%f`) plus a collision-avoidance loop as a cheap belt-and-suspenders guard. Both fixes verified via a repro script reproducing the exact GPS-then-Captioning sequence, and a new regression test, `tests/test_logging_setup.py`. **These two bugs (window-flashing, log cross-contamination) do NOT share a root cause** despite both surfacing around the GPS panel — one is the unrelated Remote Access panel's always-on status timer, the other is `logging_setup.py`'s pre-existing shared-singleton design only surfacing once two dashboard workers were actually run concurrently.

## Non-negotiable cross-cutting rules
1. **Resumability everywhere.** Every phase must be safely re-runnable without redoing work already done. Track processed files by content hash, not filename or path. (See the destination-rescan performance issue above — resumability shouldn't mean "safe but needlessly slow"; cheap pre-checks before a full hash are in scope for satisfying this rule well, not just technically.)
2. **Never silently overwrite or destroy original photos.** Phase 1 uses copy-verify-delete: copy to destination, verify via hash comparison, only then delete the source. A failed verification must leave the source in place and get logged — never delete on an unverified copy. Collision handling must never overwrite an existing file.
3. **Log everything.** Every phase needs a log the user can read after the fact to answer "what happened to file X and why." The dashboard's log viewer reads these same log files — don't create a second, separate logging path for the GUI.
4. **Config, not hardcoding.** Source/dest paths, backend choice (local model vs Claude API for captioning), batch sizes, and GPU on/off should live in a config file.
5. **JSONL for intermediate outputs** (Phase 2 captions, Phase 3 face embeddings) — appendable, resumable. SQLite is the final data layer, loaded from JSONL.
6. **Primary key = file content hash** across all DB tables, since paths will move during Phase 1 and duplicates/re-exports are likely across 25 years of photos.
7. **The GUI is a wrapper, not a parallel implementation.** The dashboard should call the same underlying functions/modules the CLI uses, not duplicate logic. `main.py`'s commands must keep working directly.
8. **At 100k+ files, favor batched/incremental real runs over one giant pass**, and favor cheap pre-checks (path/size/mtime) over full re-hashing wherever a file is very likely unchanged. Both the CLI and dashboard already support scanning a subset of `source_folders`, so folder-by-folder real runs are achievable without new code.
9. **Video (Phase 1b) reuses Phase 1's copy-verify-delete/hashing/collision/logging logic as-is — do not reimplement any of it for video.** Only the date-resolution first step (container metadata vs. EXIF) and the destination subfolder routing are actually different.
10. **Every user-facing capability must be exposed in the dashboard — not left CLI-only.** This was violated once already (GPS extraction shipped as `main.py extract-gps` with no dashboard button, and the user only discovered this after being confused why location data wasn't showing up) and the user explicitly corrected it going forward: from now on, when a session adds a new capability the user would actually want to run themselves (not an internal/dev-only script), it needs a dashboard panel or button in the SAME session that builds it — not deferred to "add a GUI for it later." CLI commands can still exist alongside (main.py stays fully usable per rule 7), but the dashboard must never be missing something the CLI can do that an end user would want.
11. **When a session modifies `review_tool.py` (or its templates/static/supporting modules), it must restart it itself before ending the session — not leave that for the user to do manually.** This is an explicit reversal of the earlier "don't kill a process you didn't start unprompted" convention, scoped specifically to `review_tool.py`: the user has explicitly requested this automation given how often stale processes serving pre-change code have caused confusion in this project. Use the restart tooling being built for this purpose (see TODO.md's "One-click restart" item) — detect any process bound to the configured `review_tool_port`, kill it/them, wait for the port to actually free, then relaunch fresh — so the session's own changes are immediately live and testable without any manual step. This does NOT extend to `dashboard.py` or any other process — the reversal is scoped to `review_tool.py` only, since it's stateless/read-only and safe to restart unprompted; other processes still follow the original "don't touch what you didn't start" convention.
