**Bug caught and fixed during testing — same class as the earlier tqdm/pythonw crash:** hachoir's own internal warning/error logging (`hachoir.core.log.Log.newMessage`) writes directly to `sys.stdout`/`sys.stderr` (`sys.stdout.flush()` unconditionally, then `sys.stderr.write(...)`). Under `pythonw.exe` (how the dashboard launches — see `Launch Dashboard.bat`), both are `None`, so ANY hachoir warning or error (routine — e.g. "Unknown MOV file type" on a corrupt/truncated/unusual video, which is expected at this library's real-world scale) would have crashed the dashboard identically to the earlier tqdm bug. Fixed in `video_date_resolver.py` at import time: `hachoir.core.config.quiet = True` plus `hachoir.core.log.log.use_print = False` (quiet alone doesn't suppress LOG_ERROR-level messages, which hit the same crash path — `use_print = False` is the actual fix). **Verified by simulating pythonw.exe** (`sys.stdout = sys.stderr = None`) against both a garbage-bytes fixture file (triggers hachoir's warning path) and real MOV/MP4 files from the library — no crash either way, correct dates still returned. This would very likely have been hit on the first real dashboard run touching video, given how common "unusual container" warnings are across 25 years / many devices — worth remembering (added to CLAUDE.md) as a pattern to check for with *any* future third-party library that does its own console/stderr output.
