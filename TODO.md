## RESOLVED (this session): Test whether face detection and captioning can safely run concurrently on the GPU

Unlike GPS/thumbnails (CPU-only, trivially safe alongside anything), both face detection (`onnxruntime-gpu`) and captioning (Ollama/`llama-server.exe`) actually compete for the SAME limited 6GB VRAM.

The real problem is GPU compute scheduling: under sustained concurrent load, `onnxruntime-gpu`'s continuous stream of small face-detection kernels appears to starve Ollama's `llama-server.exe` of GPU time almost completely — captioning did NOT crash or error, it just barely progressed at all.
- [x] **Small controlled test run, not a full production run** — solo baselines first (45 real photos captioned alone, 36 real photos face-detected alone), then a genuine concurrent test (17-photo captioning batch + 977-photo face-detection batch, started ~30s apart so both were actively computing at the same time, not just both "running").
- [x] **VRAM monitored continuously via `nvidia-smi --query-gpu` every 1-2s throughout every leg** (~3 min baseline reading, ~17 min solo-caption reading, ~40s solo-face reading, ~4 min true-concurrent reading). Baseline (idle desktop, other apps open — browser, Oculus client, Office, etc.) was already ~2,815-2,820 MiB of the 6,144 MiB total, tighter headroom than a clean-boot machine would have.
- [x] **Real numbers, this session, this hardware:**
  - Solo captioning (qwen3-vl:2b, 45 real photos from `E:\Pics\2020\2020-01`): 16m31s total, **~22.0s/file** average (notably slower than the ~7-9s/image documented in Phase 2's own earlier session — flagged as environmental variance worth knowing, not explained/investigated further this session, since this session's own solo number is what matters for the apples-to-apples comparison below).
